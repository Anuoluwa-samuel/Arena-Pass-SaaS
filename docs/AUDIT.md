## 2. What is working

- Landing page, session list and session detail render correctly against mock data.
- Session status derivation (`upcoming | open | closed | sold-out`) from a ticket window.
- Countdown timer with urgency state and odometer digits.
- Navbar with active route indicator, mobile menu, scroll shadow.
- Motion primitives (`Reveal`, `StaggerGroup`, `StaggerItem`) with reduced-motion fallbacks.
- Dark green sports theme defined as OKLCH tokens in `app/globals.css`.
- Type-check passes (`tsc --noEmit` exit 0).

## 3. What is broken or missing

### Correctness
1. **No persistence.** Creating a session in `/admin` runs a 1.5 s timer and discards the form. Payment runs a 1.6 s timer and redirects. Nothing is saved anywhere.
2. **Ticket ID is random on every render** (`app/confirmation/page.tsx`) and the player name is hard-coded to "John Doe".
3. **Capacity is hard-coded to 22**, not the required 8 teams × 4 players = 32, and there is no concept of teams or player slots.
4. **`getSessionStatus` is copy-pasted three times** (`session-card.tsx`, `sessions/[id]/page.tsx`, `admin/page.tsx`).
5. **Currency is `$`** while the product brief prices in ₦.
6. **Dead links**: navbar links to `/dashboard` and login links to `/forgot-password`; neither route exists.
7. **Mock dates are computed at module load**, so status drifts and differs between server and client renders (hydration mismatch risk).
8. **Edit/Delete menu items in admin do nothing.**
9. **"Join Waitlist" and "Download Ticket" buttons do nothing.**

### Dependencies and build
10. **`motion` is imported but not declared in `package.json`** — it is present only as an extraneous package in `node_modules`. A clean install breaks the build.
11. **`next.config.mjs` sets `typescript.ignoreBuildErrors: true`**, silently shipping type errors.
12. **Two lockfiles** (`pnpm-lock.yaml` committed, `package-lock.json` git-ignored) while the machine uses npm. Installs are non-reproducible.
13. **`styles/globals.css` is an unused duplicate** of the shadcn default theme.
14. **`lint` script has no ESLint configuration.**
15. **`package.json` name is `my-project`.**
16. Unused dependencies: `@vercel/analytics` is fine, but `embla-carousel-react`, `react-resizable-panels`, `input-otp`, `cmdk`, `vaul`, `react-day-picker`, `recharts` are only referenced by unused shadcn primitives. They are kept for now because the admin platform will use several of them (charts, command palette, drawer, calendar).

### Security
17. **Login/signup accept anything** and redirect. No credentials are checked.
18. **Card number, expiry and CVC are collected in a plain form** with a "powered by Stripe" label. Collecting raw card data in your own form is a PCI-DSS violation. Card entry must be delegated to the provider (Paystack inline/redirect, Stripe Elements).
19. `/admin` is reachable by anyone.
20. No CSRF, rate-limiting, security headers, or input validation of any kind.

## 4. What should be preserved

- The whole visual layer: theme tokens, shadcn primitives, `Navbar`, `SessionCard`, `CountdownTimer`, `AlertModal`, `ScrollCue`, `Magnetic`, `Reveal`/`StaggerGroup`/`StaggerItem`, `app/template.tsx` page transition.
- The page structure and copy of the landing page, session list and detail pages.
- The purchase-window (booking deadline) concept, which maps directly onto `booking_opens_at` / `booking_deadline`.

## 5. What should be refactored

- `Session` type moves from `components/session-card.tsx` to a domain module and gains `teamsCount`, `playersPerTeam`, `totalCapacity`, `bookedCount`, `status`, `arena`.
- `getSessionStatus` becomes one pure function in `lib/domain/session-status.ts`.
- Currency and date formatting become shared helpers (`lib/format.ts`).
- Pages become server components that load data from the database; client components are limited to interactive islands.
- `/admin` becomes a routed section with its own layout, navigation and RBAC guard instead of a single page.
- The payment page stops collecting card data and instead collects customer information, creates a booking (slot reservation) and hands off to the payment provider.

## 6. What should be replaced

- `lib/mock-data.ts` → a real database (Postgres schema via Drizzle ORM) plus a seed script for local development.
- Simulated login/signup/payment timers → real auth, booking and payment services.
- `styles/globals.css` → deleted.
- `pnpm-lock.yaml` → deleted; `package-lock.json` becomes the tracked lockfile.

## 7. Recommended architecture

```
app/
  (public pages)        server components reading via services
  admin/                admin shell (sidebar layout) + RBAC-guarded pages
  api/                  route handlers → services; uniform JSON envelope
  validate/             staff QR validation screen
server/                 server-only code (never imported by client bundles)
  db/                   drizzle schema, client (PGlite locally / pg in prod), migrations, seed
  auth/                 password hashing, server-side sessions, cookies, RBAC
  services/             sessions, bookings, tickets, payments, cms, media, notifications, audit
  payments/             PaymentProvider interface + Paystack + Mock providers
  http/                 response envelope, error mapping, validation, rate limiting
lib/                    client-safe: domain types, status logic, formatting, zod schemas, api client
components/             UI: existing primitives + admin + ticketing components
tests/                  vitest unit + integration (PGlite in-memory), playwright e2e
docs/                   architecture, database, API, runbooks
```

Key decisions and why:

- **Postgres dialect everywhere.** Local development uses PGlite (Postgres compiled to WASM, in-process, no Docker) and staging/production use a managed Postgres via `DATABASE_URL`. One schema, one migration set, real `SELECT … FOR UPDATE` row locks and CHECK constraints in both environments.
- **Booking integrity in the database.** The session row is locked inside a transaction, the atomic counter is bounded by a CHECK constraint, and each (session, team, slot) is protected by a partial unique index. Even a buggy service cannot oversell.
- **Idempotency keys** on booking creation and **provider verification** before confirmation. A ticket row has a unique `booking_id`, so a confirmed payment creates a ticket exactly once.
- **Server-side sessions** (opaque token in an httpOnly cookie, hashed at rest) rather than JWTs, so logout and privilege changes take effect immediately.
- **RBAC stored in the database** (roles → permissions) and enforced in every route handler through `requirePermission`. UI hides what the user cannot do, but the API is the authority.
- **Payment abstraction** so Paystack can be swapped for Flutterwave or Stripe without touching booking logic. Card data never touches Game Slots servers.
- **Signed QR payload.** The QR encodes `ticket_number.hmac` and nothing personal; validation checks the signature, then performs a conditional `UPDATE … WHERE status = 'CONFIRMED'` so a ticket can only be used once.
- **Multi-arena from day one.** Every session, ticket and CMS record carries `arena_id`.
